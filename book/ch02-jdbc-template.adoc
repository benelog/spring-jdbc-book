== Spring JDBC: JdbcTemplate과 NamedParameterJdbcTemplate

1장의 마지막에서 순수 JDBC의 세 가지 고통을 꼽았다.
자원 정리 상용구, checked 예외, 수동 트랜잭션 관리.
Spring JDBC는 이 중 앞의 둘을 이 장에서, 나머지 하나를 다음 두 장에서 해결한다.

Spring JDBC의 핵심은 *템플릿 콜백 패턴*이다.
커넥션 획득 → SQL 실행 → 결과 처리 → 자원 반납이라는 정해진 절차(템플릿)는 라이브러리가 수행하고, 호출하는 쪽은 그때그때 달라지는 부분(SQL, 파라미터, 행 매핑)만 채워 넣는다.
그 템플릿의 이름이 `JdbcTemplate`이고, 파라미터에 이름을 붙일 수 있게 확장한 것이 `NamedParameterJdbcTemplate`이다.

이 장의 예제 모듈은 `examples/ch02-jdbc-template`이다.
아직 Spring 컨테이너 없이, `spring-jdbc` 라이브러리만 가져다 일반 Java 코드에서 사용한다.
Spring JDBC는 프레임워크 전체를 도입하지 않아도 이렇게 라이브러리처럼 쓸 수 있다.

=== 왜 Spring JDBC인가

본격적인 사용법에 앞서, "SQL을 직접 다루는 계층"의 대표 선택지인 MyBatis와 견주어 Spring JDBC의 성격을 정리해 두자.
요지는 *배울 것은 적고, 컴파일러의 도움은 크다*는 것이다.

*초기 진입이 가볍다.*
`DataSource`만 있으면 한 줄로 시작한다.

[source,java]
----
NamedParameterJdbcTemplate jdbc = new NamedParameterJdbcTemplate(dataSource);
----

매퍼 XML, 세션 팩토리 같은 새 개념을 익힐 필요가 없다.
지금까지 배운 JDBC와 SQL, 그리고 Java 문법이 전부다.

*매핑 코드가 Java 코드라서 컴파일러가 지켜 준다.*
뒤에서 볼 `RowMapper`는 메서드가 하나뿐인 인터페이스이고, 그 안에서 생성자나 setter를 직접 호출한다.
오타가 있으면 컴파일이 되지 않고, IDE의 자동 완성·코드 추적·리팩터링이 전부 동작한다.
반면 XML이나 애너테이션 문자열 속에 적힌 `property="daekId"` 같은 오타는 빌드를 통과하고 런타임에야 드러난다.
날짜 변환, enum 변환 같은 타입 변환도 별도의 TypeHandler 없이 매핑 코드 안에서 평범한 Java 코드로 처리한다.

*동적 SQL도 Java 제어문으로 만든다.*
`<if>`, `<foreach>` 같은 태그 문법을 새로 배우는 대신 if문과 반복문으로 SQL을 조립한다.
분기 로직이 일반 코드이므로 단위 테스트와 커버리지 측정의 대상이 된다는 부수 효과도 있다.

*동작이 예측 가능하다.*
Spring JDBC는 호출한 시점에 그 SQL을 실행할 뿐, 세션 캐시나 지연 실행 같은 암묵적인 동작이 없다.
배치 실행조차 `batchUpdate`라는 별도 메서드로 의도를 드러내야 한다.

물론 Spring JDBC가 끝판왕이라는 뜻은 아니다.
SQL 문자열 자체의 타입 안전성까지 원한다면 Querydsl SQL이나 jOOQ가, 풍부한 객체 매핑이 필요하다면 JPA가 다음 선택지다.
이 책의 후반부에서 다루는 Spring Data JDBC와 Spring JDBC Plus는 Spring JDBC의 단순함을 지키면서 반복 작업을 더 줄이는 중간 지점이다.

=== 예외는 어디로 갔나: DataAccessException

위 코드 어디에도 `throws SQLException`이 없다.
Spring JDBC는 `SQLException`을 잡아 *unchecked* 예외인 `DataAccessException` 계층으로 번역해 던진다.

이 번역은 단순한 포장이 아니다.
DB마다 제각각인 에러 코드를 해석해서 `DuplicateKeyException`(키 중복), `DataIntegrityViolationException`(제약 조건 위반), `BadSqlGrammarException`(SQL 문법 오류)처럼 *의미 있는 타입*으로 바꿔 준다.
호출하는 쪽은 관심 있는 예외만 골라 잡으면 되고, 나머지는 전파되도록 두면 된다.
DB를 바꿔도 예외 타입은 그대로라는 점도 중요하다.

=== NamedParameterJdbcTemplate: 이름 있는 파라미터

물음표 파라미터는 개수가 늘어나면 순서 맞추기가 고역이 된다.

==== SQL이 XML에 살던 시절

한때 Java 진영의 SQL은 대부분 XML 파일 안에 있었다.
iBatis(지금의 MyBatis)는 매퍼 XML에 SQL을 넣는 것이 필수였고, Hibernate와 JPA도 named query를 XML 파일로 뺄 수 있었다.
SQL이 XML로 간 가장 큰 이유는 named parameter도 예외 처리 편의도 아니었다.
텍스트 블록이 없던 시절의 Java에서 여러 줄 문자열을 다루기가 너무 불편했기 때문이다.

[source,java]
----
static final String SELECT_BY_DECK_ID =
    "SELECT id, deck_id, text, meaning "
    + "FROM cards "
    + "WHERE deck_id = :deckId ";
----

DB 클라이언트에서 다듬은 SQL을 코드에 붙여 넣으려면 줄마다 따옴표와 `+`를 끼워 넣어야 했고, 반대로 코드 속 SQL을 DB 클라이언트로 가져갈 때는 그것들을 다시 걷어 내야 했다.
이 왕복이 번거로워 SQL이 통째로 XML로 옮겨 갔고, 그러자 동적 쿼리를 위한 조건문·반복문 태그와 매핑 선언까지 XML로 딸려 들어갔다.
앞의 "왜 Spring JDBC인가"에서 꼽은 XML 방식의 단점들은 그 부산물이다.

Java 15부터 정식이 된 텍스트 블록이 이 역사의 근본 원인을 제거했다.
이제 SQL을 Java 코드 안에 두는 데 편집상의 장애물은 없다.
SQL을 한곳에 모아 DBA 검수를 받는 관행이 필요하다면, XML 파일이 아니라 `CardSql`처럼 SQL 상수만 모은 클래스를 분리하는 것으로 충분하다.

==== RowMapper를 직접 안 쓰는 법: DataClassRowMapper

`cardMapper` 필드의 정체는 이것이다.

[source,java]
----
private final RowMapper<Card> cardMapper = DataClassRowMapper.newInstance(Card.class);
----

`DataClassRowMapper`는 record의 생성자 파라미터 이름과 조회 결과의 컬럼 이름을 맞춰 자동으로 매핑한다.
`deck_id`처럼 스네이크 표기 컬럼은 `deckId`처럼 캐멀 표기 프로퍼티에 알아서 연결된다.
일반 클래스의 setter 기반 매핑이 필요하면 형제인 `BeanPropertyRowMapper`를 쓴다.
자동 매핑으로 안 되는 특수한 변환이 필요할 때만 람다로 직접 `RowMapper`를 쓰면 된다.

=== 정리

이 장에서 순수 JDBC의 고통 두 가지가 사라졌다.
자원 정리 상용구는 템플릿이 삼켰고, checked `SQLException`은 의미 있는 unchecked 예외 계층으로 바뀌었다.
`DataClassRowMapper`와 `BeanPropertySqlParameterSource`는 "컬럼 ↔ 프로퍼티" 방향의 반복 작업까지 덜어 준다.

남은 하나가 트랜잭션이다.
`DeckImporter`의 commit/rollback 코드와 커넥션 돌려쓰기 문제는 아직 그대로다.
다음 장에서 Spring의 트랜잭션 추상화가 등장한다.
