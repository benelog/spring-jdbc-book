== Spring JDBC: JdbcTemplate과 NamedParameterJdbcTemplate

1장의 마지막에서 순수 JDBC의 세 가지 고통을 꼽았다.
자원 정리 상용구, checked 예외, 수동 트랜잭션 관리.
Spring JDBC는 이 중 앞의 둘을 이 장에서, 나머지 하나를 다음 두 장에서 해결한다.

Spring JDBC의 핵심은 *템플릿 콜백 패턴*이다.
커넥션 획득 → SQL 실행 → 결과 처리 → 자원 반납이라는 정해진 절차(템플릿)는 라이브러리가 수행하고, 호출하는 쪽은 그때그때 달라지는 부분(SQL, 파라미터, 행 매핑)만 채워 넣는다.
그 템플릿의 이름이 ``JdbcTemplate``이고, 파라미터에 이름을 붙일 수 있게 확장한 것이 ``NamedParameterJdbcTemplate``이다.

이 장의 예제 모듈은 ``examples/ch02-jdbc-template``이다.
아직 Spring 컨테이너 없이, `spring-jdbc` 라이브러리만 가져다 일반 Java 코드에서 사용한다.
Spring JDBC는 프레임워크 전체를 도입하지 않아도 이렇게 라이브러리처럼 쓸 수 있다.

=== 왜 Spring JDBC인가

본격적인 사용법에 앞서, "SQL을 직접 다루는 계층"의 대표 선택지인 MyBatis와 견주어 Spring JDBC의 성격을 정리해 두자.
요지는 *배울 것은 적고, 컴파일러의 도움은 크다*는 것이다.

*초기 진입이 가볍다.*
``DataSource``만 있으면 한 줄로 시작한다.

[source,java]
----
NamedParameterJdbcTemplate jdbc = new NamedParameterJdbcTemplate(dataSource);
----

매퍼 XML, 세션 팩토리 같은 새 개념을 익힐 필요가 없다.
지금까지 배운 JDBC와 SQL, 그리고 Java 문법이 전부다.

*매핑 코드가 Java 코드라서 컴파일러가 지켜 준다.*
뒤에서 볼 ``RowMapper``는 메서드가 하나뿐인 인터페이스이고, 그 안에서 생성자나 setter를 직접 호출한다.
오타가 있으면 컴파일이 되지 않고, IDE의 자동 완성·코드 추적·리팩터링이 전부 동작한다.
반면 XML이나 애너테이션 문자열 속에 적힌 `property="daekId"` 같은 오타는 빌드를 통과하고 런타임에야 드러난다.
날짜 변환, enum 변환 같은 타입 변환도 별도의 TypeHandler 없이 매핑 코드 안에서 평범한 Java 코드로 처리한다.

*동적 SQL도 Java 제어문으로 만든다.*
`<if>`, `<foreach>` 같은 태그 문법을 새로 배우는 대신 if문과 반복문으로 SQL을 조립한다.
분기 로직이 일반 코드이므로 단위 테스트와 커버리지 측정의 대상이 된다는 부수 효과도 있다.

*동작이 예측 가능하다.*
Spring JDBC는 호출한 시점에 그 SQL을 실행할 뿐, 세션 캐시나 지연 실행 같은 암묵적인 동작이 없다.
배치 실행조차 ``batchUpdate``라는 별도 메서드로 의도를 드러내야 한다.

물론 Spring JDBC가 끝판왕이라는 뜻은 아니다.
SQL 문자열 자체의 타입 안전성까지 원한다면 Querydsl SQL이나 jOOQ가, 풍부한 객체 매핑이 필요하다면 JPA가 다음 선택지다.
이 책의 후반부에서 다루는 Spring Data JDBC와 Spring JDBC Plus는 Spring JDBC의 단순함을 지키면서 반복 작업을 더 줄이는 중간 지점이다.

``JdbcTemplate``과 ``NamedParameterJdbcTemplate``은 상태를 갖지 않아 *스레드 안전*하다.
요청마다 새로 만들 필요 없이 이렇게 필드에 저장해 재사용하는 것이 표준 사용법이다.

초기화 코드에서 한 가지 더 눈여겨볼 부분은 필드의 타입이다.
``new``로 만드는 것은 ``JdbcTemplate``이지만, 필드는 ``JdbcTemplate``이 구현한 `JdbcOperations` *인터페이스* 타입으로 선언했다.
``setFetchSize``처럼 ``JdbcTemplate``에 있는 세터 계열 메서드는 이 인터페이스에 정의되어 있지 않다.
그런 설정은 초기화 시점에 끝나야 할 일이므로, SQL을 실행하는 메서드 안에서는 세터에 아예 접근할 수 없는 편이 안전하다.
IDE의 자동 완성 목록에 쿼리 실행과 무관한 메서드가 나타나지 않는 것도 소소한 장점이다.
생성자가 ``JdbcTemplate``이 아니라 ``DataSource``를 받는 구조도 같은 방향의 선택이다.
내부에서 어떤 템플릿을 쓰는지가 생성자 시그니처에 드러나지 않으므로, 나중에 다른 템플릿으로 갈아타도 이 클래스를 생성하는 코드는 바뀌지 않는다.

=== 예외는 어디로 갔나: DataAccessException

위 코드 어디에도 ``throws SQLException``이 없다.
Spring JDBC는 ``SQLException``을 잡아 *unchecked* 예외인 `DataAccessException` 계층으로 번역해 던진다.

이 번역은 단순한 포장이 아니다.
DB마다 제각각인 에러 코드를 해석해서 `DuplicateKeyException`(키 중복), `DataIntegrityViolationException`(제약 조건 위반), `BadSqlGrammarException`(SQL 문법 오류)처럼 *의미 있는 타입*으로 바꿔 준다.
호출하는 쪽은 관심 있는 예외만 골라 잡으면 되고, 나머지는 전파되도록 두면 된다.
DB를 바꿔도 예외 타입은 그대로라는 점도 중요하다.

==== checked 예외는 왜 데이터 액세스와 맞지 않나

``SQLException``을 unchecked로 바꾼 것은 `throws` 선언을 지워 주는 편의 이상의 설계 결정이다.
checked 예외는 "호출자가 잡아서 의미 있는 복구를 할 수 있다"는 전제 위에 서 있는데, 데이터 액세스에서 만나는 예외 대부분은 그 전제가 성립하지 않는다.
DB 서버와의 연결이 끊겼거나 SQL에 문법 오류가 있을 때, catch 절 안에서 할 수 있는 복구란 사실상 없다.
그런데도 컴파일러가 처리를 강요하니, 현실의 코드는 로그만 남기고 지나가거나 심하면 빈 catch로 예외를 삼키곤 했다.
삼켜진 예외는 문제를 그 자리에서 드러내는 대신, 한참 뒤 엉뚱한 곳에서 더 이해하기 어려운 오류로 나타난다.

잡지 않을 예외라면 던지는 쪽 선언도 짐이 된다.
DAO의 모든 메서드에 ``throws SQLException``이 붙는 순간 그 시그니처는 "구현이 JDBC"라는 사실을 추상화 바깥으로 누설하고, 직접 잡지 않는 호출 계층들은 잡지도 못할 예외의 `throws` 선언을 층층이 반복하게 된다.

또 하나의 문제는 ``SQLException``이라는 타입 하나가 너무 많은 상황을 뭉뚱그린다는 점이다.
접속 실패, 문법 오류, 키 중복, 제약 조건 위반이 전부 같은 타입으로 도착하고, 원인을 구분하려면 DB 벤더마다 다른 에러 코드나 SQLState 문자열을 직접 해석해야 한다.
Java 6의 JDBC 4.0이 ``SQLTransientException``(재시도하면 성공할 수도 있는 일시적 오류), ``SQLNonTransientException``(재시도해도 소용없는 오류), ``SQLRecoverableException`` 같은 하위 타입을 도입해 세분화를 시도했지만, checked라는 골격은 그대로였다.

Spring의 `DataAccessException` 계층은 이 두 문제를 함께 해결한다.
unchecked라서 `DuplicateKeyException` 뒤에 재시도나 안내 메시지 같은 의미 있는 처리를 할 수 있는 곳에서만 잡으면 되고, 계층이 세분화되어 있어 catch 대상 타입만으로 무엇이 잘못됐는지 드러난다.
같은 결론에 도달한 것은 Spring만이 아니다.
Hibernate도 3.0부터 checked 예외를 버렸고, 그 경험 위에서 표준화된 JPA의 `PersistenceException` 계층은 처음부터 unchecked다.
데이터 액세스 예외를 checked로 설계한 JDBC의 선택은 이제 Java 진영 전체가 되돌아 나온 길이라 해도 지나치지 않다.

필드 선언에 쓰인 ``NamedParameterJdbcOperations``는 ``NamedParameterJdbcTemplate``이 구현한 인터페이스다.
``JdbcTemplate``과 ``JdbcOperations``의 관계가 여기서도 똑같이 반복된다.

파라미터는 ``Map``으로 넘기는 것이 가장 간단하다.
SQL은 Java의 텍스트 블록(`"""`)으로 적어 여러 줄을 그대로 담는다.
복사해서 DB 콘솔에 붙여 실행해 볼 수 있는 형태가 유지된다는 것이 생각보다 큰 장점이다.

==== SQL이 XML에 살던 시절

한때 Java 진영의 SQL은 대부분 XML 파일 안에 있었다.
iBatis(지금의 MyBatis)는 매퍼 XML에 SQL을 넣는 것이 필수였고, Hibernate와 JPA도 named query를 XML 파일로 뺄 수 있었다.
SQL이 XML로 간 가장 큰 이유는 named parameter도 예외 처리 편의도 아니었다.
텍스트 블록이 없던 시절의 Java에서 여러 줄 문자열을 다루기가 너무 불편했기 때문이다.

[source,java]
----
static final String SELECT_BY_DECK_ID =
    "SELECT id, deck_id, text, meaning "
    + "FROM cards "
    + "WHERE deck_id = :deckId ";
----

DB 클라이언트에서 다듬은 SQL을 코드에 붙여 넣으려면 줄마다 따옴표와 ``+``를 끼워 넣어야 했고, 반대로 코드 속 SQL을 DB 클라이언트로 가져갈 때는 그것들을 다시 걷어 내야 했다.
이 왕복이 번거로워 SQL이 통째로 XML로 옮겨 갔고, 그러자 동적 쿼리를 위한 조건문·반복문 태그와 매핑 선언까지 XML로 딸려 들어갔다.
앞의 "왜 Spring JDBC인가"에서 꼽은 XML 방식의 단점들은 그 부산물이다.

Java 15부터 정식이 된 텍스트 블록이 이 역사의 근본 원인을 제거했다.
이제 SQL을 Java 코드 안에 두는 데 편집상의 장애물은 없다.
SQL을 한곳에 모아 DBA 검수를 받는 관행이 필요하다면, XML 파일이 아니라 ``CardSql``처럼 SQL 상수만 모은 클래스를 분리하는 것으로 충분하다.

==== RowMapper를 직접 안 쓰는 법: DataClassRowMapper

`cardMapper` 필드의 정체는 이것이다.

[source,java]
----
private final RowMapper<Card> cardMapper = DataClassRowMapper.newInstance(Card.class);
----

``DataClassRowMapper``는 record의 생성자 파라미터 이름과 조회 결과의 컬럼 이름을 맞춰 자동으로 매핑한다.
``deck_id``처럼 스네이크 표기 컬럼은 ``deckId``처럼 캐멀 표기 프로퍼티에 알아서 연결된다.
일반 클래스의 setter 기반 매핑이 필요하면 형제인 ``BeanPropertyRowMapper``를 쓴다.
자동 매핑으로 안 되는 특수한 변환이 필요할 때만 람다로 직접 ``RowMapper``를 쓰면 된다.

=== SimpleJdbcInsert: SQL 없이 insert

이 장을 마치기 전에, 초기화 코드에만 등장하고 설명을 미뤄 둔 ``SimpleJdbcInsert``를 살펴보자.

insert 문은 유난히 기계적이다.
컬럼 이름을 나열하고, 똑같은 개수의 플레이스홀더를 한 번 더 나열한다.
컬럼이 하나 늘 때마다 양쪽을 같이 고쳐야 하지만, 정작 문장 안에 로직이라 할 만한 것은 없다.
``SimpleJdbcInsert``는 이 반복을 통째로 없앤다.
테이블 이름만 알려 주면 DB 메타데이터에서 컬럼 목록을 읽어 insert SQL을 스스로 만들어 실행한다.

``executeAndReturnKey``는 insert를 실행하고 채번된 키를 돌려준다.
`decks` 테이블에 컬럼이 늘어도 이 메서드에서 고칠 SQL이 없다.
Map에 값을 하나 더 담으면 되고, 담지 않은 컬럼은 insert 문에서 빠져 DB의 default 값이 적용된다.

한 가지 주의할 점이 있다.
Map의 키는 Java 프로퍼티 이름이 아니라 *컬럼 이름*이다.
`deck_id` 컬럼에 값을 넣으려면 키도 ``"deck_id"``여야 하고, ``"deckId"``라고 적으면 오류조차 없이 그 컬럼만 조용히 insert에서 빠진다.

객체의 프로퍼티를 그대로 쓰고 싶다면 이번에도 ``BeanPropertySqlParameterSource``가 해결한다.
이쪽은 `deckId` 프로퍼티를 `deck_id` 컬럼에 알아서 연결해 준다.

앞에서 본 KeyHolder 방식의 ``insert``와 하는 일은 같고, 차이는 SQL이 코드에 보이느냐뿐이다.
컬럼이 많은 테이블의 단순 insert라면 ``SimpleJdbcInsert``가 코드를 크게 줄여 주고, DB 함수 호출이나 select 결과의 insert처럼 SQL 수준의 제어가 필요하면 SQL을 직접 쓰는 쪽이 맞다.

몇 가지 세부 사항도 알아 두자.
메타데이터 조회는 최초 실행 때 한 번만 일어나고, 그때 만들어진 insert 문이 이후 계속 재사용된다.
insert 대상 컬럼을 명시적으로 제한하려면 ``usingColumns``를 쓴다.
채번 키가 필요 없으면 `execute`, 여러 건을 한 번에 넣을 때는 ``executeBatch``를 쓴다.
같은 원리로 스토어드 프로시저 호출을 감싸 주는 형제 클래스 ``SimpleJdbcCall``도 있다.

=== JdbcClient: 하나로 합쳐진 fluent API

=== 정리

이 장에서 순수 JDBC의 고통 두 가지가 사라졌다.
자원 정리 상용구는 템플릿이 삼켰고, checked ``SQLException``은 의미 있는 unchecked 예외 계층으로 바뀌었다.
``DataClassRowMapper``와 ``BeanPropertySqlParameterSource``는 "컬럼 ↔ 프로퍼티" 방향의 반복 작업까지 덜어 주고, ``SimpleJdbcInsert``는 insert SQL 작성 자체를 생략하게 해 준다.
두 템플릿의 갈래를 하나의 fluent API로 합친 ``JdbcClient``라는 새 입구도 생겼다.

남은 하나가 트랜잭션이다.
``DeckImporter``의 commit/rollback 코드와 커넥션 돌려쓰기 문제는 아직 그대로다.
다음 장에서 Spring의 트랜잭션 추상화가 등장한다.
