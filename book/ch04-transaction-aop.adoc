== AOP 트랜잭션: @Transactional

3장의 ``TransactionTemplate``은 트랜잭션 상용구를 크게 줄였지만, 여전히 메서드 본문이 `execute` 블록에 싸여 있다.
트랜잭션은 "이 메서드 전체"라는 경계 선언일 뿐인데, 그 선언이 코드 들여쓰기 한 겹을 차지한다.
이 장에서는 선언을 애너테이션 한 줄로 옮기고 본문에서는 트랜잭션 코드를 완전히 지운다.

이를 가능하게 하는 원리가 AOP(Aspect-Oriented Programming, 관점 지향 프로그래밍)다.
트랜잭션 처리처럼 여러 클래스에 가로로 걸쳐 반복되는 관심사를, 각 메서드에 흩어 놓는 대신 한 곳에 모아 두고 프레임워크가 알아서 끼워 넣게 하는 기법이다.

예제 모듈은 ``examples/ch04-transaction-aop``다.
이 장부터는 객체를 직접 조립하는 대신 Spring 컨테이너(ApplicationContext)가 조립을 맡는다.
그래서 의존성 목록에도 컨테이너가 들어온다.

=== 동작 원리: 프록시

애너테이션만 붙였는데 트랜잭션이 어떻게 시작될까?
Spring 컨테이너는 ``@Transactional``이 붙은 빈을 등록할 때 그 빈을 감싸는 *프록시*(proxy)를 대신 등록한다.
프록시는 원본과 같은 타입으로 보이지만, 메서드 호출을 가로채 "트랜잭션 시작 → 원본 메서드 호출 → 커밋/롤백"을 수행한다.
3장에서 ``TransactionTemplate.execute``가 하던 일을 프록시가 대신한다.

주입받은 빈의 실제 클래스를 찍어 보면 확인할 수 있다.

``DeckService``를 상속해 만들어진 프록시 클래스다.

프록시 방식이라는 사실에서 실무에서 중요한 주의점 하나가 따라 나온다.
*같은 클래스 안에서 자기 메서드를 호출하면(self-invocation) 트랜잭션이 적용되지 않는다.*
내부 호출은 프록시를 거치지 않고 원본 객체의 메서드로 직행하기 때문이다.
`@Transactional` 메서드는 다른 빈에서 호출될 때만 프록시의 가로채기가 동작한다는 것을 기억해 두자.

=== 함정: checked 예외는 롤백되지 않는다

=== 커밋된 뒤에 할 일: @TransactionalEventListener

덱 가져오기가 끝나면 알림을 보내고 싶다고 하자.
가장 쉬운 코드는 ``importDeck`` 마지막 줄에서 알림 API를 호출하는 것인데, 이 코드는 두 가지 문제를 안고 있다.

첫째, *외부 호출이 트랜잭션 안에 들어온다*.
알림 서버의 응답이 3초 걸리면 DB 커넥션도 3초를 더 붙들려 있는다.
외부 시스템이 느려지는 순간 커넥션 풀이 마르는, 1장의 항공사 장애와 같은 구도다.
둘째, *롤백돼도 알림은 이미 나갔다*.
알림을 보낸 뒤 트랜잭션이 실패하면, 저장되지 않은 덱의 완료 알림이 발송되고 만다.

두 문제의 공통 원인은 "커밋 후에 해야 할 일"이 트랜잭션 안에 있다는 것이다.
Spring은 이를 이벤트로 분리하는 길을 제공한다.
서비스는 트랜잭션 안에서 이벤트를 **발행**하기만 한다.

일반 ``@EventListener``였다면 발행 즉시 실행되지만, ``@TransactionalEventListener``의 기본 동작은 *발행한 트랜잭션이 커밋된 뒤*(``AFTER_COMMIT``)로 실행을 미루는 것이다.

트랜잭션이 롤백되면 발행된 이벤트는 조용히 버려진다.

`phase` 속성으로 실행 시점을 바꿀 수 있다.
롤백됐을 때 실행하는 ``AFTER_ROLLBACK``, 결과와 무관하게 실행하는 ``AFTER_COMPLETION``, 커밋 직전에 끼어드는 ``BEFORE_COMMIT``이 있다.

두 가지 주의 사항이 있다.
``AFTER_COMMIT`` 리스너는 이미 커밋이 끝난 뒤에 실행되므로, 그 안에서 DB를 더 수정하려면 ``@Transactional(propagation = REQUIRES_NEW)``로 새 트랜잭션을 열어야 한다.
그리고 리스너는 기본적으로 발행한 스레드에서 동기로 실행되므로, 응답 시간에서 알림 발송 시간까지 떼어 내고 싶다면 ``@Async``를 함께 붙여 별도 스레드로 넘긴다.
어느 쪽이든 커넥션은 커밋 시점에 이미 반납된 뒤라, 서두에 말한 "외부 호출이 커넥션을 붙드는" 문제는 생기지 않는다.

==== 애플리케이션 컨텍스트 캐싱

컨텍스트를 띄우는 테스트는 직접 조립하는 테스트보다 느릴 수밖에 없다.
Spring 테스트 프레임워크는 이 비용을 **컨텍스트 캐싱**으로 줄인다.
설정 클래스, 활성 프로파일, 테스트 프로퍼티 같은 구성 정보의 조합이 같으면, 같은 JVM 안에서는 컨텍스트를 처음 한 번만 만들고 이후 테스트 클래스들이 재사용한다.
같은 설정을 가리키는 테스트 클래스가 열 개여도 컨텍스트 로딩과 스키마 초기화는 한 번이라는 뜻이다.

여기서 실천 지침 두 가지가 나온다.
첫째, *테스트 컨텍스트는 작게 만든다*.
필요한 빈 몇 개만 올린 컨텍스트는 1초도 안 되어 뜨므로, 캐싱과 합치면 "컨테이너 테스트는 느리다"는 통념이 무색해진다.
꼭 필요한 객체만 등록하라는 원칙은 운영 컨텍스트에도 그대로 통한다.
부팅이 빨라지고 의도하지 않은 의존 관계가 자동으로 주입될 위험도 줄어든다.
둘째, *설정을 공유한다*.
컨텍스트를 쓰는 테스트가 이 장처럼 하나뿐이면 위와 같은 정적 내부 클래스로 충분하지만, 그런 테스트가 늘어나면 공용 설정 클래스를 떼어내 함께 참조해야 캐시가 적중한다.
클래스마다 설정이 조금씩 다르면 그 수만큼 컨텍스트가 새로 뜬다.

공용 설정 클래스에는 ``@Configuration``을 붙이지 않는 편이 안전할 때가 있다.
``@SpringJUnitConfig``에 직접 지정한 클래스는 ``@Configuration``이 없어도 `@Bean` 메서드가 동작한다.
반면 ``@Configuration``이 붙으면 컴포넌트 스캔의 대상이 되므로, 스캔 범위가 겹치는 다른 테스트가 이 테스트 전용 설정까지 의도치 않게 끌어들일 수 있다.

==== 데이터 정리: 롤백이냐 삭제냐

컨텍스트가 재사용된다는 것은 그 안의 ``DataSource``, 즉 내장 DB도 여러 테스트가 공유한다는 뜻이다.
한 테스트가 남긴 데이터가 다음 테스트의 검증 결과를 바꾸지 않으려면 정리 전략이 필요하다.

spring-test의 대표 기법은 **테스트 트랜잭션 롤백**이다.
테스트 클래스에 ``@Transactional``을 붙이면 각 테스트 메서드가 트랜잭션 안에서 실행되고, 메서드가 끝나면 자동으로 롤백되어 DB가 테스트 전 상태로 돌아간다.
컨텍스트에 `PlatformTransactionManager` 빈만 있으면 되는데, ``AppConfig``가 이미 등록해 두었다.

그런데 이 장의 테스트는 그 기법 대신 ``@AfterEach``에서 delete 문으로 지운다.

테스트 대상이 하필 **트랜잭션 그 자체**이기 때문이다.
테스트가 트랜잭션을 먼저 열어 두면, `REQUIRED` 전파의 `@Transactional` 메서드는 새 트랜잭션을 만드는 대신 테스트의 트랜잭션에 참여한다.
그러면 "checked 예외인데 커밋되었다"를 증명할 실제 커밋이 일어나지 않고, 롤백 여부도 테스트 트랜잭션에 묻혀 관찰할 수 없다.
커밋과 롤백을 검증하는 테스트는 트랜잭션 바깥에서 지켜봐야 한다.

반대로 테스트 대상이 트랜잭션을 스스로 관리하지 않는다면(저장소 계층이 대표적이다) 롤백 기법이 잘 맞는다.
다음 장에서 볼 ``@JdbcTest``가 이 기법을 자동으로 적용해 주는 슬라이스다.
다만 롤백 기법에도 한계는 있다.
실행 시간이 길거나 대량 데이터를 다루는 테스트를 하나의 트랜잭션으로 묶으면, 특히 여러 사람이 공유하는 개발 DB에서는 락으로 다른 작업을 방해할 수 있다.

==== 빈을 주입받는 여러 방법

이 장의 테스트는 필드에 ``@Autowired``를 붙여 빈을 받았다.
운영 코드라면 생성자 주입을 권하지만, 테스트 클래스는 누가 생성자를 직접 호출할 일이 없으므로 필드 주입의 단점이 문제 되지 않는다.

한두 테스트 메서드만 쓰는 빈이라면 메서드 파라미터로 받는 편이 어디에 필요한지를 더 잘 드러낸다.

[source,java]
----
@Test
void importDeck(@Autowired DeckService deckService) {
    // ...
}
----

생성자 주입을 고수하고 싶다면 ``@TestConstructor(autowireMode = AutowireMode.ALL)``을 테스트 클래스에 붙이는 방법도 있다.
어느 방식이든 동작은 같으니, 테스트 메서드가 늘어날 때 중복이 덜 생기는 쪽을 고르면 된다.
``@Autowired``가 붙는 곳이 지나치게 많아진다면 주입 방식을 바꾸기보다, 테스트 클래스가 다루는 관심사가 너무 넓지 않은지부터 의심하자.

=== 정리

1장에서 꼽은 순수 JDBC의 세 가지 고통이 모두 사라졌다.
자원 정리는 ``JdbcTemplate``이, 예외 번역은 `DataAccessException` 계층이, 트랜잭션은 `@Transactional` 프록시가 맡는다.
비즈니스 코드에는 SQL과 로직만 남았다.

대신 새로운 종류의 앎이 필요해졌다.
선언 한 줄 뒤에서 무슨 일이 벌어지는지(프록시가 끼어드는 곳, 내부 호출의 함정, checked 예외의 롤백 규칙)를 이해하고 있어야 한다.
추상화의 대가는 언제나 이런 식이다.

여기까지의 설정(DataSource, 트랜잭션 매니저, 컴포넌트 스캔)은 매 프로젝트 똑같이 반복된다.
다음 장의 Spring Boot가 이 반복마저 가져간다.
