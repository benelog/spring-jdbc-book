== JDBC: 모든 것의 바탕이 되는 표준

Java 애플리케이션이 관계형 데이터베이스와 대화하는 방법은 결국 하나로 수렴한다.
JDBC(Java Database Connectivity)다.
JPA를 쓰든 MyBatis를 쓰든, 이 책에서 다룰 Spring JDBC와 Spring Data JDBC를 쓰든, 맨 밑바닥에서 SQL을 나르는 것은 언제나 JDBC다.
그래서 첫 장은 JDBC 표준 API 그 자체에서 출발한다.

JDBC는 구현체가 아니라 **인터페이스의 묶음**이다.
`java.sql` 패키지의 `Connection`, `Statement`, `ResultSet` 같은 인터페이스가 표준을 정의하고, 각 데이터베이스 벤더가 자기 DB에 맞는 구현체(JDBC 드라이버)를 제공한다.
우리가 쓰는 H2라면 `com.h2database:h2` 의존성 안에 드라이버가 들어 있다.
덕분에 애플리케이션 코드는 표준 인터페이스에만 의존하고, DB를 바꾸면 드라이버와 SQL 방언만 바뀐다.

이 장의 예제 모듈은 ``examples/ch01-jdbc-basics``다.
Spring 없이 JDK와 H2 드라이버, 커넥션 풀 라이브러리(HikariCP)만 쓴다.
빌드 파일의 의존성 선언이 그 사실을 그대로 보여 준다.

==== try-with-resources 이전의 자원 정리

이 "반드시 닫기"가 얼마나 만만치 않은 일이었는지는 try-with-resources(Java 7)가 없던 시절의 권장 코드를 보면 실감이 난다.

[source,java]
----
Connection conn = null;
PreparedStatement pstmt = null;
ResultSet rs = null;
try {
    conn = dataSource.getConnection();
    pstmt = conn.prepareStatement("select ...");
    rs = pstmt.executeQuery();
    while (rs.next()) {
        // ...
    }
} catch (SQLException e) {
    // ...
} finally {
    if (rs != null) try { rs.close(); } catch (Exception ignored) {}
    if (pstmt != null) try { pstmt.close(); } catch (Exception ignored) {}
    if (conn != null) try { conn.close(); } catch (Exception ignored) {}
}
----

핵심은 finally 안에서 close 호출 하나하나를 다시 try-catch로 감싼 부분이다.
close 역시 ``SQLException``을 던질 수 있으므로, 앞선 close의 예외를 잡아 주지 않으면 뒤의 ``conn.close()``가 실행되지 않기 때문이다.
"Connection을 닫으면 Statement도 함께 닫힌다"는 스펙만 믿기도 어렵다.
커넥션 풀에서 얻은 커넥션의 ``close()``는 실제로 연결을 끊는 것이 아니라 풀에 반환하는 것이라, ``Statement``까지 정리된다고 장담할 수 없다.
이렇게 코딩하지 않은 시스템은 한참 잘 돌다가 DB가 "maximum open cursors exceeded" 같은 에러를 내기 시작할 때에야 문제를 알게 된다.

《Release It》(마이클 나이가드)의 첫 사례 연구가 바로 이 문제다.
미국 한 대형 항공사의 예약 시스템에서, finally 절이 예외 처리 없이 `stmt.close()` 다음에 ``conn.close()``를 부르는 구조로 되어 있었다.
정기 점검을 위해 이중화된 DB 한쪽을 수동으로 fail-over하는 순간 죽은 연결 위의 ``stmt.close()``가 예외를 던졌고, 그 뒤의 ``conn.close()``는 실행되지 않았다.
반환되지 않은 커넥션 탓에 풀은 곧 바닥났고, 새 커넥션을 기다리는 스레드들이 줄줄이 블록되면서 예약 시스템 전체가 세 시간 동안 멈췄다.
close 한 줄의 실수라기보다는, 제대로 쓰기가 이토록 어려운 API의 문제다.

try-with-resources는 이 중 순서와 예외 문제를 언어 차원에서 해결했다.
선언의 역순으로 닫아 주고, 닫는 중에 난 예외가 본래 예외를 삼키지 않도록 suppressed 예외로 붙여 준다.
그래도 자원 세 개를 얻고 닫는 구조 자체를 메서드마다 써야 한다는 사실은 달라지지 않았다.

=== 트랜잭션: commit과 rollback

Flashcard의 CSV 가져오기를 생각해 보자.
덱 하나를 만들고 그 안에 카드 수십 장을 넣는데, 중간에 한 장이 실패하면 어떻게 해야 할까?
반쯤 들어간 덱이 남는 것보다는 전부 없던 일로 되돌리는 편이 낫다.

=== DataSource: 커넥션을 얻는 표준 통로

=== 정리: 순수 JDBC의 한계

JDBC만으로도 필요한 일은 전부 할 수 있다.
그러나 이 장의 코드에는 반복되는 고통이 세 가지 있었다.

1. *자원 정리 상용구*: 메서드마다 반복되는 커넥션·문장·결과 집합의 획득과 반납.
2. *checked 예외*: 모든 메서드에 전염되는 `throws SQLException`. 게다가 ``SQLException``은 DB마다 다른 에러 코드를 담고 있을 뿐, 무엇이 잘못됐는지 타입으로 구분해 주지 않는다.
3. *수동 트랜잭션 관리*: 커넥션을 인자로 끌고 다니게 만드는 commit/rollback 코드.

이 고통은 JDBC만큼이나 오래된 것이라, 자원 정리를 대신해 주는 도우미 라이브러리(Apache Commons DbUtils가 대표적이다)도 일찍부터 있었다.
다음 장부터 Spring JDBC가 이 셋을 순서대로 지워 나간다.
