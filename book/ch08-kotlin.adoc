== Kotlin 프로젝트 팁

이 장은 보너스다.
Spring JDBC 생태계를 Kotlin 프로젝트에서 쓸 때 도움이 되는 문법과 관례를 모았다.
Spring Framework는 Kotlin을 공식 지원하며, 앞 장들에서 다룬 Spring JDBC, Spring Data JDBC, Spring JDBC Plus가 모두 Kotlin에서 그대로 동작한다.

Kotlin + Spring 프로젝트라면 빼놓지 않고 쓰는 플러그인이다.

=== checked 예외가 없는 언어의 예외 처리

Kotlin에는 checked 예외가 없다.
``SQLException``을 던지는 Java 메서드를 호출해도 컴파일러가 try-catch나 `throws` 선언을 요구하지 않는다.
2장에서 본 "catch 절에서 할 것이 없는데도 처리를 강요당하는" 문제를 Kotlin은 언어 차원에서 없앴다.
Kotlin 공식 문서도 이 설계의 근거를 든다.
대규모 코드베이스에서 checked 예외는 생산성을 떨어뜨리고, 빈 catch 블록으로 예외를 삼키는 코드를 오히려 늘린다는 것이다.
JDBC가 checked 예외로 설계된 뒤 Java 진영이 쌓은 이런 경험을, 뒤에 나온 언어가 문법에 반영한 결과라 볼 수 있다.

그렇다고 Spring JDBC의 예외 번역이 Kotlin에서 덜 중요해지는 것은 아니다.
checked냐 아니냐는 "처리를 강요당하는가"의 문제일 뿐이다.
`DataAccessException` 계층의 본질은 DB마다 다른 에러 코드를 의미 있는 타입으로 바꿔 주는 번역에 있다.
Kotlin에서 순수 JDBC를 직접 쓰면 처리를 강요당하지는 않는다.
하지만 DB 오류가 종류와 관계없이 ``SQLException`` 하나로 오는 것은 그대로다.
`DuplicateKeyException` 같은 세분화된 타입만 골라 잡는 코드는 Kotlin에서도 똑같이 유효하다.

반대 방향의 상호 운용도 알아 두자.
Kotlin 함수가 던지는 예외를 Java 쪽에서 checked 예외로 다뤄야 한다면 ``@Throws(SQLException::class)`` 애너테이션으로 바이트코드에 `throws` 선언을 넣을 수 있다.
Spring JDBC를 쓰는 코드에서는 unchecked 예외만 오가므로 이런 선언이 필요할 일은 거의 없다.

=== 생태계 참고 사항

* *Spring Data JDBC와 data class*: 6장의 엔티티도 data class로 쓸 수 있다.
Spring Data JDBC는 변경을 추적하지 않고 ``save``에 넘긴 객체의 상태를 그대로 저장하므로, `val` 프로퍼티로 만든 불변 객체를 ``copy``로 바꿔 저장하는 방식을 그대로 쓸 수 있다.
* *Spring JDBC Plus*: Kotlin을 공식 지원하며, `spring-data-jdbc-plus-sql-kotlin` 모듈이 Kotlin DSL을 제공한다.
7장의 SQL 클래스와 리포지토리 구현 패턴도 Kotlin에서 동일하게 쓸 수 있다.
* *coroutine*: 이 책의 범위 밖이지만, JDBC는 블로킹 API이므로 coroutine에서 쓸 때는 ``withContext(Dispatchers.IO)`` 블록 안에서 호출하는 것이 관례다.
3장에서 본 대로 트랜잭션은 스레드에 바인딩되므로, 트랜잭션 경계와 그 안의 DB 호출은 전부 같은 ``withContext`` 블록 안에 두어야 한다.
중간에 suspend되어 스레드가 바뀌면 그 뒤의 호출은 트랜잭션 밖에서 실행된다.

=== 다음으로

JDBC 표준에서 출발해 템플릿, 트랜잭션 추상화, 자동 설정, 리포지토리, 확장 라이브러리, 그리고 다른 언어까지 올라왔다.
기술 스택의 레이어는 모두 다뤘지만, 각 기술에는 아직 소개하지 못한 기능이 남아 있다.
마지막 두 장에서 Spring Data JDBC와 Spring JDBC Plus의 심화 기능을 마저 둘러보고 책을 맺는다.
