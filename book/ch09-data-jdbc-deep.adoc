== Spring Data JDBC 더 깊이: 조회, 값 매핑, 생명주기

6장에서는 Spring Data JDBC의 뼈대인 애그리거트와 리포지토리를 익혔다.
그 뼈대만으로도 앱은 만들어지지만, 실무 규모가 되면 곧 다음 질문들이 따라온다.
카드가 수천 장일 때 목록 화면은 어떻게 끊어 보여 주나?
"생성일·수정일 컬럼을 모든 테이블에 두라"는 팀 규칙은 누가 채우나?
태그 목록처럼 테이블로 만들기는 과한 값은 어디에 담나?

이 장은 그 질문들에 답하는 Spring Data JDBC의 나머지 도구들을 다룬다.
예제 모듈은 ``examples/ch09-data-jdbc-deep``이고, 6장처럼 덱과 카드 두 애그리거트로 이루어진 테스트 중심 모듈이다.
의존성도 6장과 똑같다. 이 장의 심화 기능들에 새 의존성은 필요 없다.

=== @Embedded: 테이블 없는 값 객체

덱마다 "하루에 새 카드 몇 장, 복습 몇 장까지"라는 복습 정책을 두고 싶다.
정책은 항상 덱과 함께 읽고 쓰는 값이므로 테이블을 따로 만들 이유가 없다.

=== AggregateReference: 애그리거트 사이의 타입 있는 id 참조

=== @Modifying: 여러 행을 고치는 쿼리

"덱을 합치면서 카드를 전부 옮기기"처럼 여러 행을 한 번에 고치는 작업은, 카드를 한 장씩 불러 저장하는 것보다 UPDATE 한 방이 낫다.

----
include::{examples}/ch09-data-jdbc-deep/src/test/java/flashcard/deep/CardRepositoryTest.java[tag=modifying]

반환 타입을 ``int``로 하면 영향받은 행 수를 돌려준다.
2장에서 ``JdbcTemplate.update``가 돌려주던 그 값이다.
주의할 점도 2장과 같다. 이 UPDATE는 애그리거트를 거치지 않고 테이블에 직접 닿으므로, 낙관적 잠금(`@Version`)이나 이 장 뒷부분의 콜백·감사는 적용되지 않는다.

=== 감사: 생성·수정 시각 자동 기록

"모든 테이블에 `created_at`, `updated_at` 컬럼을 둔다"는 규칙은 흔하지만, 모든 저장 코드에서 손으로 채우면 반드시 빠뜨리는 곳이 생긴다.
감사(auditing)를 켜면 프레임워크가 저장 시점에 대신 채운다.

``AbstractJdbcConfiguration``은 Spring Data JDBC의 기반 설정 클래스로, `userConverters` 같은 확장 지점을 열어 둔다.
Spring Boot의 자동 설정도 내부적으로 이 클래스의 서브클래스라서, 우리가 서브클래스를 직접 두면 Boot 쪽이 자리를 비켜 준다.

여기서 6장의 슬라이스 테스트 주의점이 하나 더 늘어난다.
``@DataJdbcTest``는 일반 ``@Configuration`` 클래스를 컴포넌트 스캔에서 제외한다.
그래서 테스트에서 이 설정을 쓰려면 명시적으로 가져와야 한다.

애플리케이션에서는 잘 돌던 코드가 테스트에서만 깨지는, 진단 비용이 큰 유형의 문제이므로 기억해 둘 만하다.

=== 정리

이 장의 도구들은 성격이 하나로 모인다. *반복되는 관심사를 선언 한 줄로 옮기는 것.*
페이지 계산은 `Pageable` 파라미터로, 시각 기록은 애너테이션으로, 값 변환은 컨버터로, 공백 정리는 콜백으로.
서비스 코드에는 도메인 로직만 남는다.

그리고 이 장의 어떤 기능도 6장의 원칙을 깨지 않았다.
쿼리가 나가는 지점은 여전히 코드에 보이고, 복잡한 조회는 여전히 SQL로 적는다.
다음 장에서는 같은 태도로 Spring JDBC Plus의 남은 기능들을 마저 살펴보고 책을 맺는다.
