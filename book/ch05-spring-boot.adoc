== Spring Boot: spring-boot-starter-jdbc와 첫 웹 앱

앞 장까지 우리는 ``DataSource``를 만들고, 템플릿을 만들고, 트랜잭션 매니저를 등록하는 조립 코드를 직접 썼다.
이 조립은 어느 프로젝트에서나 거의 같다.
Spring Boot는 "클래스패스에 있는 것을 보고 뻔한 조립을 대신 해 주는" 자동 설정(auto-configuration)으로 이 반복을 없앤다.

이 장에서는 ``spring-boot-starter-jdbc``로 데이터 액세스 기반을 받고, 그 위에 Flashcard의 첫 웹 버전을 만든다.
덱과 카드를 관리하고 카드를 넘겨 보는, 아직 복습 일정은 없는 기본판이다.
예제 모듈은 ``examples/ch05-boot-jdbc``다.

=== 테스트: @JdbcTest와 @SpringBootTest

Boot의 테스트 지원 중 데이터 액세스에 유용한 것이 슬라이스 테스트 ``@JdbcTest``다.
전체 컨텍스트 대신 JDBC 관련 빈만 띄우고, ``DataSource``를 내장 메모리 DB로 바꿔치기한다.

``@JdbcTest``는 각 테스트를 트랜잭션으로 감싸고 끝나면 롤백하므로, 테스트끼리 데이터가 섞이지 않는다.
4장에서 소개한 테스트 트랜잭션 롤백 기법을 슬라이스가 대신 적용해 주는 것이다.

==== 컨텍스트 캐싱과 프로퍼티

``@SpringBootTest``는 전체 컨텍스트를 띄우므로, 4장에서 설명한 컨텍스트 캐싱의 덕을 가장 크게 보는 쪽이자 캐시를 가장 쉽게 흘리는 쪽이기도 하다.
캐시 키에는 ``properties``로 덮어쓴 값도 들어간다.
웹 테스트 클래스를 하나 더 만들면서 datasource URL만 ``jdbc:h2:mem:another``로 바꿔 적으면, 구성이 다르다고 판단되어 전체 테스트를 돌릴 때 무거운 컨텍스트가 한 번 더 뜬다.
이런 클래스가 늘수록 전체 테스트 시간이 컨텍스트 로딩으로 채워지므로, 프로퍼티 조합은 통째로 공유해야 한다.
간단하게는 설정 문자열을 상수로 뽑아 함께 쓰고, 클래스가 많아지면 ``@SpringBootTest``와 프로퍼티를 묶은 메타 애너테이션을 만들어 붙인다.

컨텍스트를 공유하면 그 안의 DB 상태도 공유된다는 점은 기억해 두자.
``@SpringBootTest``는 ``@JdbcTest``와 달리 테스트를 트랜잭션으로 감싸 주지 않는다.
그래서 위의 웹 테스트는 "덱을 만들면 덱 상세로 이동한다"처럼 누적된 데이터에 흔들리지 않는 조건만 검증했다.
행 개수를 세는 식의 검증이 필요하다면 테스트가 만든 데이터를 직접 정리하거나, 테스트에 ``@Transactional``을 직접 붙여 롤백되게 해야 한다.

==== 실제 DB로 테스트: Testcontainers

지금까지의 테스트는 전부 H2 위에서 돌았다.
빠르고 간편하지만, 운영 DB가 PostgreSQL이나 MySQL이라면 H2 테스트는 "우리 DB에서도 되는지"까지 보증하지 못한다.
DB마다 SQL 방언, 타입 처리, 잠금 동작이 미묘하게 다르기 때문이다.
이 간극을 메우는 실무 표준이 *Testcontainers*다.
테스트가 시작될 때 Docker로 진짜 DB를 컨테이너로 띄우고, 끝나면 지운다.

의존성 세 가지와 운영 DB의 드라이버를 테스트 스코프에 추가한다.

핵심은 ``@ServiceConnection``이다.
컨테이너가 뜨면 Boot가 그 접속 정보(URL, 계정)를 읽어 ``DataSource``를 스스로 구성한다.
프로퍼티를 한 줄도 적지 않았는데 `spring.sql.init.mode=always` 설정 덕분에 ``schema.sql``까지 새 DB에 그대로 적용된다.
``@JdbcTest``의 "내장 DB로 바꿔치기"도 서비스 커넥션이 있으면 자동으로 물러나므로, H2 테스트와 같은 애너테이션 구성을 그대로 쓸 수 있다.
`static` 필드에 ``@Container``를 붙였으므로 컨테이너는 클래스당 한 번만 뜨고, 트랜잭션 롤백 격리는 H2 때와 동일하게 동작한다.

그렇다고 모든 테스트를 컨테이너로 돌리자는 뜻은 아니다.
컨테이너 기동에는 초 단위의 시간이 들고 Docker가 있는 환경이 필요하다(``disabledWithoutDocker = true``는 Docker가 없으면 실패 대신 건너뛰게 한다).
자주 도는 저장소 테스트는 가볍게 H2로 돌리고, DB 방언을 타는 쿼리나 릴리스 전 검증처럼 정확성이 중요한 자리에 Testcontainers를 두는 조합이 실용적이다.

=== 가상 스레드와 JDBC

JDBC는 *블로킹* API다.
쿼리가 DB에서 도는 동안 호출한 스레드는 결과가 올 때까지 멈춰서 기다린다.
전통적인 플랫폼 스레드 시절에는 이것이 확장성의 벽이었다.
스레드 하나가 메모리를 크게 차지하는 비싼 자원이라 톰캣은 기본 200개로 스레드 수를 묶어 두었고, 느린 쿼리를 기다리며 잠든 스레드가 그 자리를 차지하면 새 요청은 줄을 서야 했다.
이 벽을 넘겠다고 논블로킹 스택(WebFlux와 R2DBC)으로 갈아타는 선택지도 있었지만, 코드 전체가 리액티브 스타일로 바뀌는 큰 공사였다.

JDK 21에서 정식이 된 *가상 스레드*가 이 그림을 바꿨다.
가상 스레드는 수만 개를 만들어도 부담이 없을 만큼 가볍고, JDBC 호출로 블로킹되면 그 자리를 차지하는 대신 실행 중이던 OS 스레드를 놓아 준다.
블로킹 API인 JDBC를 *한 줄도 고치지 않고* 논블로킹 스택에 준하는 동시성을 얻는 것이다.
Boot에서는 프로퍼티 하나로 켠다.

----

이 설정 하나로 톰캣의 요청 처리와 ``@Async`` 실행 등이 가상 스레드로 옮겨 간다.
초기에는 `synchronized` 블록 안에서 블로킹되면 OS 스레드를 놓지 못하는 pinning 문제가 있어 오래된 JDBC 드라이버와의 궁합이 걱정거리였지만, 이 책이 기준으로 삼는 JDK 25에서는 언어 차원에서 해소되었다(JDK 24의 JEP 491).

다만 가상 스레드는 스레드라는 병목을 없앨 뿐, *커넥션이라는 병목은 그대로 남긴다*는 점을 분명히 하자.
동시에 처리 중인 요청이 1만 개가 되어도 DB 커넥션은 여전히 풀 크기(HikariCP 기본 10개)만큼이다.
예전에는 톰캣 스레드 200개가 유량을 제한하는 역할을 겸했지만, 그 제한이 사라지면 몰려든 요청이 전부 커넥션 풀 앞에 줄을 서고, 풀의 대기 시간 초과(connection timeout) 오류가 새로운 첫 번째 병목으로 드러난다.
가상 스레드를 켠 뒤에는 풀 크기와 대기 시간 설정을 부하에 맞게 다시 살펴야 하고, "트랜잭션 안에서 느린 외부 호출을 하지 않는다"는 4장의 원칙은 오히려 더 중요해진다.
커넥션을 오래 붙드는 코드의 비용은 스레드가 아무리 많아져도 사라지지 않기 때문이다.

=== 정리

설정 코드가 프로퍼티 몇 줄로 줄었고, 그 위에 실제로 쓸 수 있는 웹 앱이 올라갔다.
중요한 것은 Boot가 등록해 준 빈들이 전부 앞 장에서 우리가 직접 만들던 바로 그 객체라는 점이다.
자동 설정이 낯설게 느껴질 때는 "4장에서 내가 직접 하던 조립을 Boot가 대신했을 뿐"이라고 번역하면 된다.

지금까지는 SQL과 매핑을 전부 손으로 썼다.
다음 장에서는 그중 뻔한 CRUD를 프레임워크에 맡기는 Spring Data JDBC를 본다.
