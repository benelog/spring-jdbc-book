== Spring JDBC Plus와 Flashcard 완성

이 책이 쌓아 올린 마지막 레이어, Spring JDBC Plus다.
네이버가 만들어 공개한 Spring Data JDBC 확장 라이브러리로, 사내 여러 서비스에서 쓰이며 다듬어졌다.
설계 방향은 한 문장으로 요약할 수 있다.
*Spring Data JDBC의 리포지토리 편의는 유지하되, 커스텀 SQL도 리포지토리의 정식 구성 요소로 다룬다.*

6장에서 남긴 아쉬움을 돌아보면 이 라이브러리가 무엇을 채우는지 보인다.

* ``@Query``의 SQL마다 칼럼 목록을 나열하는 반복 → 엔티티 정의에서 SELECT 칼럼 목록을 생성해 주는 `SqlGeneratorSupport`.
* SQL이 애너테이션 속 문자열이어서 Java 코드로 조립할 수 없는 문제 → SQL은 SQL 클래스로, 실행은 리포지토리 구현으로 분리하는 `JdbcRepositorySupport`.
* ``save``의 insert/update 자동 판단 → 의도를 드러내는 `insert`/`update` 메서드가 있는 `JdbcRepository` 인터페이스.

이 장에서는 Spring JDBC Plus의 사용법을 익히면서, "들어가며"에서 약속한 Flashcard의 요구사항 전부(간격 반복 복습, 오늘 복습 큐, 재도전 라운드, 태그, 스마트 덱, 통계, CSV)를 완성한다.
예제 모듈은 ``examples/ch07-jdbc-plus``다.

6장에서 배운 식별자 인용 규칙에 따라, 이 모듈의 엔티티들은 전부 대문자 이름의 ``@Table``을 달고 있다.

.완성판 스키마 ERD: 카드를 중심으로 복습 상태·기록·태그가 연결되고, smart_deck은 독립 테이블이다
image::ch07-erd.png[완성판 스키마 ERD,880]

설계에서 눈여겨볼 결정은 두 가지다.

*카드는 독립 애그리거트다.*
6장에서는 덱 애그리거트가 카드를 포함했지만, 완성판에서 카드는 복습 상태·기록·태그가 모두 가리키는 조회의 중심이다.
카드를 덱 애그리거트의 일부로 두면 카드 한 장을 고치거나 태그를 붙일 때마다 덱 전체를 다시 저장하게 된다.
카드 한 장을 찾는 조회도 덱을 거쳐야 한다.
그래서 덱과 카드는 각각의 애그리거트로 두고 ``deck_id``로만 참조한다.

.애그리거트 경계의 변화: 6장에서는 덱이 카드를 포함했고, 7장에서는 카드가 독립 애그리거트가 된다
image::ch07-aggregate-boundary.png[6장과 7장의 애그리거트 경계,880]

*복습 "상태"와 복습 "기록"을 분리했다.*
``review_state``는 카드마다 한 행으로 현재 일정과 누적 성적을 담고, ``review_log``는 판정 한 번마다 한 행씩 쌓인다.
"오늘 복습 큐"는 상태를, 통계는 기록을 읽는다.
상태는 기록에서 다시 계산할 수 있는 값이다.
하지만 큐를 조회할 때마다 전체 기록을 집계하면 기록이 쌓일수록 조회가 느려지므로, 계산 결과를 따로 저장해 두었다(비정규화).

=== 리포지토리: 인터페이스, SQL, 구현의 3분할

*(3) 구현*: ``JdbcRepositorySupport``를 상속하고 커스텀 인터페이스를 구현한다.
Spring Data는 리포지토리 인터페이스가 상속한 인터페이스마다 "그 이름 + ``Impl``" 클래스를 찾아, 해당 메서드 호출을 그 클래스에 위임한다.
``CardRepository``가 ``CardRepositoryCustom``을 상속하므로 ``findDue`` 호출은 ``CardRepositoryImpl``로 넘어간다.

`sqls` 필드는 생성자에서 ``sqls(CardSql::new)``로 만들어 둔 SQL 클래스의 인스턴스다.
``mapParameterSource()``는 이름 있는 파라미터를 담을 ``MapSqlParameterSource``를 새로 만들어 주는 상위 클래스의 도우미다.

여기서 ``JdbcRepository``에서 나뉘어 있는 ``insert``와 ``update``를 쓴다.
복습 상태가 없으면 `insert`, 있으면 ``update``다.
이 코드만 보면 id가 null인지로 분기하므로 ``save``가 안에서 하는 판별과 다를 것이 없어 보인다.
차이는 그 판별이 통하지 않는 경우에 드러난다.
``save``는 id가 있으면 기존 행으로 보고 UPDATE를 실행한다.
그래서 다른 시스템에서 받은 id를 그대로 쓰는 경우처럼 id를 미리 정해 넣는 새 엔티티는 ``save``로 저장할 수 없다.
`insert`/``update``가 나뉘어 있으면 새 행인지 아닌지를 프레임워크 규칙이 아니라 코드가 정한다.
실행되는 SQL도 메서드 이름 그대로라 읽는 사람이 추측할 것이 없다.

날짜 기준값은 SQL의 ``now()``가 아니라 서비스에서 계산해 파라미터로 넘긴다.
그러면 리포지토리 테스트에서 기준 시각을 원하는 값으로 정해, 실행할 때마다 같은 결과가 나오게(결정적으로) 검증할 수 있다.
한 요청 안의 여러 쿼리가 같은 기준 시각을 쓰는 것도 보장된다.
서비스 자체는 아직 ``LocalDateTime.now()``를 직접 부르므로, 서비스 테스트까지 결정적으로 만들려면 ``Clock``을 주입해야 한다.
이 책에서는 거기까지 다루지 않는다.

=== 정리

Spring JDBC Plus는 새로운 패러다임이 아니라 코드를 어디에 둘지 다시 정리한 라이브러리다.
SQL은 SQL 클래스에, 실행 코드는 리포지토리 구현에 두고, 표준 CRUD는 인터페이스 상속으로 얻는다.
그 결과 커스텀 SQL이 많은 실무형 앱에서도 코드마다 둘 곳이 정해진다.

완성된 앱의 데이터 액세스 코드를 살펴보면 이 책이 지나온 레이어가 모두 쓰이고 있다.
스키마와 SQL(1장), 이름 있는 파라미터와 매핑(2장), 트랜잭션 경계(3~4장), 자동 설정과 테스트 슬라이스(5장), 애그리거트와 리포지토리(6장), 그리고 그 위에 커스텀 SQL 지원을 더한 Plus(7장).
아래 레이어를 알고 있으므로, 위 레이어의 기능이 맞지 않는 곳에서는 SQL과 ``NamedParameterJdbcTemplate``을 직접 쓰는 쪽으로 내려갈 수 있다.
