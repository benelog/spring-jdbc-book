== Spring JDBC Plus와 Flashcard 완성

마지막 층이다.
Spring JDBC Plus는 네이버가 만들어 공개한 Spring Data JDBC 확장 라이브러리로, 사내 여러 서비스에서 쓰이며 다듬어졌다.
방향은 명확하다. *Spring Data JDBC의 리포지토리 편의는 유지하되, 커스텀 SQL을 일급 시민으로 대접한다.*

6장에서 남긴 아쉬움을 돌아보면 이 라이브러리가 무엇을 채우는지 보인다.

* `@Query`의 SQL마다 컬럼 목록을 나열하는 반복 → 엔티티 정의에서 SELECT 컬럼 목록을 생성해 주는 `SqlGeneratorSupport`.
* SQL 문자열과 실행 코드가 애너테이션에 뒤섞이는 문제 → SQL은 SQL 클래스로, 실행은 리포지토리 구현으로 분리하는 `JdbcRepositorySupport`.
* `save`의 insert/update 자동 판단 → 의도를 드러내는 `insert`/`update` 메서드를 가진 `JdbcRepository` 인터페이스.

이 장에서는 Spring JDBC Plus의 사용법을 익히면서, 서문에서 약속한 Flashcard의 요구사항 전부 — 간격 반복 복습, 오늘 복습 큐, 재도전 라운드, 태그, 스마트 덱, 통계, CSV — 를 완성한다.
예제 모듈은 `examples/ch07-jdbc-plus`다.

Plus의 리포지토리 자동 설정은 표준 Spring Data JDBC 리포지토리 자동 설정과 겹치지 않도록, 표준 쪽이 꺼져 있을 때만 동작하게 만들어져 있다.
그래서 표준을 끄고 Plus를 켠다.
리포지토리를 만들어 주는 주체가 바뀔 뿐, 엔티티 매핑 등 나머지는 전부 Spring Data JDBC 그대로다.

또 하나, 클래스패스에 Spring Data 모듈이 여럿이면 Spring Data는 strict 모드로 들어가 *`@Table`이 붙은 엔티티만* 리포지토리 대상으로 인정한다.
6장에서 배운 식별자 인용 규칙에 따라, 이 모듈의 엔티티들은 전부 대문자 이름의 `@Table`을 달고 있다.

.완성판 스키마 ERD: 카드를 중심으로 복습 상태·기록·태그가 연결되고, smart_deck은 독립 테이블이다
image::ch07-erd.png[완성판 스키마 ERD,880]

설계에서 눈여겨볼 결정 두 가지.

*카드는 독립 애그리거트다.*
6장에서는 덱이 카드를 품었지만, 완성판에서 카드는 복습 상태·기록·태그와 연결되는 조회의 중심이다.
덱 애그리거트에 묶어 두면 카드 한 장을 판정할 때마다 덱 전체를 다시 저장하게 된다.
그래서 덱과 카드는 각각의 애그리거트로 두고 `deck_id`로만 참조한다.

*복습 "상태"와 복습 "기록"을 분리했다.*
`review_state`는 카드마다 한 행으로 현재 일정과 누적 성적을 담고, `review_log`는 판정 한 번마다 한 행씩 쌓인다.
"오늘 복습 큐"는 상태를, 통계는 기록을 읽는다.
상태는 기록으로부터 다시 계산할 수 있는 값이지만, 큐 조회 때마다 전체 기록을 집계할 수는 없으므로 비정규화해 둔 것이다.

=== 정리

Spring JDBC Plus는 새로운 패러다임이 아니라 배치의 재조정이다.
SQL은 SQL 클래스에, 실행 코드는 리포지토리 구현에, 표준 CRUD는 인터페이스 상속에.
그 결과 커스텀 SQL이 많은 실무형 앱에서도 각 코드가 제자리를 갖는다.

완성된 앱의 데이터 액세스 코드를 훑어보면 이 책이 지나온 층이 모두 살아 있다.
스키마와 SQL(1장), 이름 있는 파라미터와 매핑(2장), 트랜잭션 경계(3~4장), 자동 설정과 테스트 슬라이스(5장), 애그리거트와 리포지토리(6장), 그리고 그것들을 묶는 Plus(7장).
아래층을 알기에 위층의 선택이 자유롭다.
