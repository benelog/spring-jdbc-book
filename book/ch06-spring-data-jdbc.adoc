== Spring Data JDBC: 리포지토리와 애그리거트

`insert into cards ...`, `select ... where id = :id`, `delete from ...`.
5장까지 우리가 쓴 SQL의 상당수는 어느 테이블에나 똑같이 생긴 기본 CRUD였다.
Spring Data JDBC는 이 뻔한 부분을 인터페이스 선언만으로 만들어 주면서도, JPA 같은 기계 장치(영속성 컨텍스트, 지연 로딩, 변경 감지)는 들이지 않는다.
"ORM의 편의 중 단순한 것만, Spring JDBC의 투명함은 그대로"가 이 기술의 설계 철학이다.

=== 애그리거트: 함께 저장되고 함께 지워지는 단위

Spring Data JDBC의 중심 개념은 도메인 주도 설계(DDD)에서 온 *애그리거트*(aggregate)다.
"항상 함께 저장되고 함께 지워지는 객체 묶음"으로, 묶음의 대표를 애그리거트 루트라 한다.
덱과 카드로 말하면, 카드가 덱을 통해서만 만들어지고 지워지는 모델에서는 덱이 루트다.

=== 리포지토리: 선언이 곧 구현

리포지토리는 인터페이스 선언만으로 완성된다.

[source,java,indent=0]
----
include::{examples}/ch06-data-jdbc/src/main/java/flashcard/datajdbc/DeckRepository.java[tag=class]
----

``ListCrudRepository``를 상속하는 것만으로 `save`, `findById`, `findAll`, `deleteById` 등이 생긴다.
여기에 세 가지 방식의 조회가 공존한다.

1. *상속받은 CRUD*: 구현 없이 제공.
2. *메서드 이름 파생 쿼리*: ``findByNameContaining``처럼 이름 규칙으로 쿼리를 생성.
3. *`@Query`*: 복잡한 조회는 SQL을 직접. 2장에서 배운 이름 있는 파라미터가 그대로 쓰인다.

``findAllSummaries``처럼 엔티티가 아닌 record(`DeckSummary`)를 돌려주는 조회 전용 쿼리도 ``@Query``로 자연스럽게 처리된다.
"기본은 자동, 복잡한 것은 SQL"이라는 균형이 Spring Data JDBC를 쓰는 감각이다.

=== 엔티티 설계: 선을 넘지 않게

애그리거트와 리포지토리라는 도구를 얻었으니, 그 도구로 엔티티를 어떻게 설계할지의 원칙도 정리해 두자.
요지는 하나다. *엔티티에 책임을 몰아주지 않는다.*

*엔티티를 바깥 레이어까지 내보내지 않는다.*
엔티티 클래스를 API 응답이나 화면 모델로 그대로 내보내면 당장은 편하지만, 그 순간부터 엔티티는 저장과 표현이라는 두 주인을 섬긴다.
응답마다 감출 필드가 달라 JSON 제어 애너테이션이 쌓이고, 화면 요구가 바뀔 때마다 도메인 클래스도 고쳐야 하고, 한 클래스에 퍼시스턴스·직렬화·API 문서화 프레임워크의 애너테이션이 뒤엉킨다.
이 책의 예제가 화면에는 ``DeckSummary`` 같은 조회 전용 record를 따로 두는 이유가 이것이다.
바깥으로 나가는 데이터는 용도에 맞는 전달용 클래스(DTO)에 옮겨 담고, 엔티티는 저장 모델의 자리에 남긴다.

*역참조를 끌어모으는 만능 클래스를 경계한다.*
객체 참조가 공짜처럼 느껴지기 시작하면 이런 클래스가 만들어진다.

[source,java]
----
public class Member {              // 앱의 모든 것이 모여드는 곳
    private List<Deck> decks;
    private List<StudyLog> studyLogs;
    private List<Badge> badges;
    // 테이블이 늘어날 때마다 여기도 늘어난다
}
----

"회원 클래스를 보면 그 팀의 ORM 사용 성숙도를 알 수 있다"는 우스갯소리가 있을 만큼 흔한 함정이다.
회원의 덱 목록이 필요한 것은 특정 화면의 조회 요구이지, 회원이라는 개념의 일부가 아니다.
이런 요구는 해당 리포지토리의 조회 메서드와 조회 전용 record로 풀고, 엔티티에는 "함께 저장되고 함께 지워지는" 것만 남긴다.
회원을 읽을 때마다 앱 전체가 딸려 오는 모델은 조회 성능 문제이기 이전에 경계 붕괴의 신호다.

*애그리거트 사이는 id로 참조한다.*
앞 절 마지막의 원칙을 한 걸음 더 밀고 가 보자.
애그리거트는 곧 트랜잭션과 잠금의 범위, "엄격한 일관성을 지켜야 하는 경계"다.
덱이 회원 **객체**를 참조하면 덱을 저장하는 작업이 회원의 일관성까지 떠안는 모양이 되지만, ``Long memberId``처럼 **id**로만 참조하면 저장 단위가 명확해진다.
다른 애그리거트의 내용이 필요하면 그쪽 리포지토리로 조회하면 된다.
9장에서 소개할 ``AggregateReference``는 이 id 참조에 "어느 애그리거트의 id인가"라는 타입 정보까지 입혀 준다.

*지연 로딩이 없는 것은 결핍이 아니라 설계 압력이다.*
JPA에 익숙하다면 Spring Data JDBC에 지연 로딩(lazy loading)이 없다는 점이 불편할 수 있다.
그러나 지연 로딩이 절실하다는 것 자체가 "이 묶음은 사실 항상 함께 쓰이는 묶음이 아니다"라는 신호다.
항상 통째로 로딩해도 될 만큼 애그리거트를 작게 자르면 지연 로딩은 필요 없어지고, Spring Data JDBC는 처음부터 그 크기의 애그리거트를 전제로 만들어졌다.
불편이 느껴지는 대목은 프레임워크의 한계이기 이전에 모델을 다시 볼 기회다.

*세터 대신 의도가 담긴 메서드를 둔다.*
엔티티가 저장 모델의 자리에 있다고 해서 게터·세터만 있는 데이터 자루일 필요는 없다.
앞에서 본 ``Deck``이 이미 그렇게 되어 있다.
`setCards` 대신 ``addCard``와 ``removeCard``가 있고, `setName` 대신 ``rename``이 있다.
의도가 이름에 드러나고, 상태 변경에 따르는 정합성 검사를 넣을 자리도 그 메서드 안에 자연스럽게 생긴다.
카드 목록을 밖으로 내줄 때 복사본(`List.copyOf`)을 돌려주는 것도 같은 맥락으로, 애그리거트의 상태는 애그리거트의 메서드를 통해서만 바뀌게 지킨다.

이 원칙들은 Spring Data JDBC만의 것이 아니라 어떤 퍼시스턴스 기술에서든 통하는 설계 이야기다.
다만 Spring Data JDBC는 지연 로딩을 주지 않고 애그리거트 단위 저장만 주는 식으로, 이 원칙들을 **프레임워크 차원에서 부드럽게 강제**한다.
편의 기능이 많은 기술일수록 설계 원칙은 개발자의 절제에 맡겨지는데, 이 기술은 애초에 선을 넘기 어렵게 만들어 둔 셈이다.

=== 함정: 식별자 인용과 H2

이 장의 엔티티에서 눈에 걸리는 부분이 있었을 것이다.

[source,java]
----
@Table("DECKS")
...
@MappedCollection(idColumn = "DECK_ID", keyColumn = "CARD_INDEX")
----

왜 대문자일까?
Spring Data JDBC는 SQL을 생성할 때 식별자를 따옴표로 감싼다(quoting).
따옴표로 감싼 식별자는 대소문자를 구별하는데, H2는 따옴표 없이 만든 테이블·칼럼 이름을 **대문자**로 저장한다.
즉 ``create table decks ...``로 만든 테이블의 실제 이름은 ``DECKS``이고, 애너테이션에 ``"decks"``라고 적으면 ``"decks"``라는 소문자 이름을 찾다가 실패한다.

클래스·필드 이름에서 *유도되는* 이름(`Deck` → `DECK`, `cardCount` → `CARD_COUNT`)은 프레임워크가 DB 관례에 맞춰 대문자로 만들어 주므로 문제가 없다.
문제는 애너테이션에 *직접 적은* 이름뿐이다. 그래서 직접 적을 때는 H2가 저장하는 형태인 대문자로 맞췄다.
PostgreSQL은 반대로 소문자로 저장하므로, DB를 옮길 때 이 차이가 흔한 이식성 함정이 된다.

=== 정리

기본 CRUD는 선언으로, 복잡한 조회는 여전히 SQL로.
Spring Data JDBC는 2장에서 익힌 Spring JDBC 위에 얇게 얹히는 기술이라, 아래 레이어의 지식이 그대로 통한다.

다만 실무 규모의 앱을 만들다 보면 아쉬움이 생긴다.
``@Query``에 적는 SQL이 늘어날수록 칼럼 목록 나열이 반복되고, `save` 하나로 insert와 update를 겸하는 설계는 "새 객체인지 아닌지"의 판단을 프레임워크에 맡긴다.
이 아쉬움을 노린 확장 라이브러리가 다음 장의 Spring JDBC Plus다.
그리고 다음 장에서 드디어 Flashcard를 요구사항 전부와 함께 완성한다.
