== Spring Data JDBC: 리포지토리와 애그리거트

`insert into cards ...`, `select ... where id = :id`, `delete from ...`.
5장까지 우리가 쓴 SQL의 상당수는 어느 테이블에나 똑같이 생긴 기본 CRUD였다.
Spring Data JDBC는 이 뻔한 부분을 인터페이스 선언만으로 만들어 주면서도, JPA가 쓰는 장치(영속성 컨텍스트, 지연 로딩, 변경 감지)는 두지 않는다.
"ORM의 편의 중 단순한 것만, Spring JDBC의 투명함은 그대로"가 이 기술의 설계 철학이다.

용어 둘을 정리하고 시작한다.
*엔티티*(entity)는 테이블의 한 행과 대응하는 저장 모델 객체다.
2장부터 쓴 ``Card`` record가 이미 그 역할이었고, 이 장부터는 애너테이션으로 테이블과의 대응을 선언한다.
*리포지토리*(repository)는 엔티티를 저장하고 조회하는 객체다.
앞 장들에서 "저장소"라 부르며 직접 만들던 클래스와 역할이 같다.
이 책은 직접 만든 클래스를 저장소, Spring Data가 인터페이스 선언에서 만들어 주는 것을 리포지토리로 구분해 부른다.

=== 애그리거트: 함께 저장되고 함께 지워지는 단위

Spring Data JDBC의 중심 개념은 도메인 주도 설계(DDD)에서 온 *애그리거트*(aggregate)다.
"항상 함께 저장되고 함께 지워지는 객체 묶음"으로, 묶음의 대표를 애그리거트 루트라 한다.
덱과 카드로 말하면, 카드가 덱을 통해서만 만들어지고 지워지는 모델에서는 덱이 루트다.

``@Table``이 대응하는 테이블을, ``@Id``가 기본 키 필드를 지정한다.
나머지 필드는 필드 이름에서 유도한 칼럼 이름으로 짝지어지므로 애너테이션이 없다.
유도 규칙은 이 장 뒷부분의 식별자 인용 절에서 다룬다.
``@MappedCollection``이 "덱 하나에 카드 여러 장"을 표현한다.
`cards` 테이블의 `deck_id` 칼럼이 소속을, `card_index` 칼럼이 리스트 안의 순서를 담는다.
카드 쪽에는 이 두 칼럼에 해당하는 필드가 아예 없다는 점이 인상적이다.
소속과 순서는 애그리거트 구조가 이미 표현하고 있으므로 프레임워크가 대신 관리한다.

=== 리포지토리: 선언이 곧 구현

리포지토리는 인터페이스 선언만으로 완성된다.

----
include::{examples}/ch06-data-jdbc/src/main/java/flashcard/datajdbc/DeckRepository.java[tag=class]
----

구현 클래스는 어디에도 없다.
Spring Data가 애플리케이션이 시작될 때 이 인터페이스를 구현하는 프록시를 만들어 빈으로 등록한다.
서비스는 4장의 ``@Transactional`` 프록시처럼 그 빈을 주입받아 쓴다.
타입 인자 ``<Deck, Long>``은 이 리포지토리가 다루는 엔티티와 그 id의 타입이다.

``ListCrudRepository``를 상속하는 것만으로 `save`, `findById`, `findAll`, `deleteById` 등이 생긴다.
이 인터페이스에는 세 가지 방식의 조회가 함께 들어 있다.

1. *상속받은 CRUD*: 구현 없이 제공.
2. *메서드 이름 파생 쿼리*: ``findByNameContaining``처럼 이름 규칙으로 쿼리를 생성.
3. *`@Query`*: 복잡한 조회는 SQL을 직접. 2장에서 배운 이름 있는 파라미터가 그대로 쓰이고, SQL의 ``:deckId``는 ``@Param("deckId")``가 붙은 메서드 파라미터와 짝지어진다.

``findAllSummaries``처럼 엔티티가 아닌 record(`DeckSummary`)를 돌려주는 조회 전용 쿼리도 ``@Query``로 자연스럽게 처리된다.
"기본은 자동, 복잡한 것은 SQL"이 Spring Data JDBC를 쓰는 기본 방식이다.

=== 엔티티 설계: 원칙을 지키기 쉽게

애그리거트와 리포지토리라는 도구를 얻었으니, 엔티티를 설계하는 원칙도 정리해 두자.
요지는 하나다.
*엔티티에 책임을 몰아주지 않는다.*

*엔티티를 바깥 레이어까지 내보내지 않는다.*
엔티티 클래스를 API 응답이나 화면 모델로 그대로 내보내면 당장은 편하지만, 그 순간부터 클래스 하나가 저장 구조와 응답 형식을 함께 책임진다.
응답마다 감출 필드가 달라 `@JsonIgnore` 같은 JSON 제어 애너테이션이 쌓인다.
화면 요구가 바뀔 때마다 도메인 클래스도 고쳐야 한다.
한 클래스에 퍼시스턴스·직렬화·API 문서화 프레임워크의 애너테이션이 뒤섞인다.
이 책의 예제가 화면에는 ``DeckSummary`` 같은 조회 전용 record를 따로 두는 이유가 이것이다.
바깥으로 나가는 데이터는 용도에 맞는 전달용 클래스(DTO)에 옮겨 담고, 엔티티는 저장 모델로만 쓴다.

*역참조를 끌어모으는 만능 클래스를 경계한다.*
객체 참조가 공짜처럼 느껴지기 시작하면 이런 클래스가 만들어진다.

[source,java]
----
public class Member {              // 앱의 모든 것이 모여드는 곳
    private List<Deck> decks;
    private List<StudyLog> studyLogs;
    private List<Badge> badges;
    // 테이블이 늘어날 때마다 여기도 늘어난다
}
----

"회원 클래스를 보면 그 팀의 ORM 사용 성숙도를 알 수 있다"는 우스갯소리가 있을 만큼 흔한 함정이다.
회원의 덱 목록이 필요한 것은 특정 화면의 조회 요구이지, 회원이라는 개념의 일부가 아니다.
이런 요구는 해당 리포지토리의 조회 메서드와 조회 전용 record로 풀고, 엔티티에는 "함께 저장되고 함께 지워지는" 것만 남긴다.
회원을 읽을 때마다 덱, 학습 기록, 배지까지 함께 읽히는 모델은 조회 성능 문제이기 이전에 애그리거트 경계를 잘못 잡았다는 신호다.

*애그리거트 사이는 id로 참조한다.*
앞 절 마지막에 나온 id 참조 원칙을 좀 더 자세히 보자.
애그리거트는 트랜잭션과 잠금의 범위이자 "엄격한 일관성을 지켜야 하는 경계"다.
덱이 회원 **객체**를 참조하면 덱을 저장할 때 회원 객체의 상태까지 신경 써야 한다.
``Long memberId``처럼 **id**로만 참조하면 덱을 저장하는 작업은 덱 애그리거트 안에서 끝난다.
다른 애그리거트의 내용이 필요하면 그쪽 리포지토리로 조회하면 된다.
9장에서 소개할 ``AggregateReference``는 이 id 참조에 "어느 애그리거트의 id인가"라는 타입 정보를 더한다.

*지연 로딩이 없는 것은 기능 부족이 아니라 설계를 되돌아보게 하는 제약이다.*
JPA에 익숙하다면 Spring Data JDBC에 지연 로딩(lazy loading)이 없다는 점이 불편할 수 있다.
그러나 지연 로딩이 절실하다는 것 자체가 "이 묶음은 사실 항상 함께 쓰이는 묶음이 아니다"라는 신호다.
항상 통째로 로딩해도 될 만큼 애그리거트를 작게 자르면 지연 로딩은 필요 없어진다.
Spring Data JDBC는 처음부터 그 크기의 애그리거트를 전제로 만들어졌다.
불편이 느껴지는 대목은 프레임워크의 한계이기 이전에 모델을 다시 볼 기회다.

*세터 대신 의도가 담긴 메서드를 둔다.*
엔티티가 저장 모델이라고 해서 필드와 접근자만 있는 클래스일 필요는 없다.
앞에서 본 ``Deck``이 이미 그렇게 되어 있다.
`setCards` 대신 ``addCard``와 ``removeCard``가 있고, `setName` 대신 ``rename``이 있다.
의도가 이름에 드러나고, 상태 변경에 따르는 정합성 검사(예: 빈 이름 거부)도 그 메서드 안에 넣으면 된다.
카드 목록을 밖으로 내줄 때 복사본(`List.copyOf`)을 돌려주는 것도 같은 이유다.
밖에서 받은 목록은 수정할 수 없으므로, 애그리거트의 상태는 애그리거트의 메서드로만 바뀐다.

이 원칙들은 Spring Data JDBC만의 것이 아니라 어떤 퍼시스턴스 기술에서든 통하는 설계 이야기다.
다만 Spring Data JDBC는 지연 로딩을 주지 않고 애그리거트 단위 저장만 주는 식으로, 이 원칙들을 **프레임워크 차원에서 강제**한다.
편의 기능이 많은 기술일수록 설계 원칙은 개발자의 절제에 맡겨지는데, 이 기술은 애초에 원칙을 어기기 어렵게 만들어 두었다.

=== 함정: 식별자 인용과 H2

이 장의 엔티티에서 눈에 띄는 부분이 있었을 것이다.

[source,java]
----
@Table("DECKS")
...
@MappedCollection(idColumn = "DECK_ID", keyColumn = "CARD_INDEX")
----

질문은 둘이다.
왜 테이블 이름을 직접 적었고, 왜 대문자인가.

이름을 직접 적은 이유는 유도 규칙과 스키마가 다르기 때문이다.
클래스 이름에서 유도되는 테이블 이름은 단수형 ``DECK``인데 1장부터 쓴 테이블은 복수형 ``decks``라, 대소문자와 무관하게 ``@Table``로 이름을 알려 주어야 한다.
`cards` 테이블의 ``Card``도 마찬가지다.

대문자인 이유는 식별자 인용 때문이다.
Spring Data JDBC는 SQL을 생성할 때 식별자를 따옴표로 감싼다(quoting).
따옴표로 감싼 식별자는 대소문자를 구별하는데, H2는 따옴표 없이 만든 테이블·칼럼 이름을 **대문자**로 저장한다.
즉 ``create table decks ...``로 만든 테이블의 실제 이름은 ``DECKS``이고, 애너테이션에 ``"decks"``라고 적으면 ``"decks"``라는 소문자 이름을 찾다가 실패한다.
클래스·필드 이름에서 *유도되는* 이름(`cardCount` → `CARD_COUNT`)은 프레임워크가 DB 관례에 맞춰 대문자로 만들어 주므로 문제가 없다.
문제는 애너테이션에 *직접 적은* 이름뿐이다.
그래서 직접 적을 때는 H2가 저장하는 형태인 대문자로 맞췄다.

PostgreSQL은 반대로 따옴표 없는 식별자를 소문자로 저장하므로, 대문자로 적어 둔 이름은 DB를 옮기는 순간 테이블을 찾지 못하는 원인이 된다.
말로만 듣는 것보다 5장의 Testcontainers로 확인하는 편이 빠르다.
같은 `decks` 테이블을 소문자 이름으로 가리키는 테스트용 엔티티를 하나 더 두고, 두 엔티티를 PostgreSQL 컨테이너에서 저장해 보자.

운영 DB가 따로 있다면 처음부터 두 방법 중 하나를 고르는 편이 낫다.
하나는 애너테이션에 이름을 직접 적지 않는 것이다.
테이블 이름을 클래스 이름과 맞추거나(`deck`), 복수형 같은 규칙을 `NamingStrategy` 빈으로 정해 두면, 유도된 이름은 어느 DB에서든 프레임워크가 그 DB의 저장 방식에 맞춘다.
다른 하나는 애너테이션에 운영 DB가 저장하는 형태(PostgreSQL이라면 소문자)로 적고, H2 쪽에서 대소문자 차이를 없애는 것이다.
H2 URL에 ``CASE_INSENSITIVE_IDENTIFIERS=TRUE``를 붙이면 따옴표로 감싼 식별자도 대소문자를 구별하지 않으므로, 대문자 ``DECKS``와 소문자 ``decks`` 둘 다 같은 테이블을 찾는다(``IdentifierCaseInsensitiveH2Test``).
이 책의 예제는 끝까지 H2에서 실행하므로 가장 단순한 대문자 표기를 택했다.

=== 정리

기본 CRUD는 선언으로, 복잡한 조회는 여전히 SQL로.
Spring Data JDBC는 2장에서 익힌 Spring JDBC 위에서 SQL을 실행하는 기술이라, 아래 레이어의 지식이 그대로 통한다.

다만 실무 규모의 앱을 만들다 보면 아쉬움이 생긴다.
``@Query``에 적는 SQL이 늘어날수록 칼럼 목록 나열이 반복되고, `save` 하나로 insert와 update를 겸하는 설계는 "새 객체인지 아닌지"의 판단을 프레임워크에 맡긴다.
이 아쉬움을 채우려고 만든 확장 라이브러리가 다음 장의 Spring JDBC Plus다.
그리고 다음 장에서 드디어 Flashcard를 요구사항 전부와 함께 완성한다.
